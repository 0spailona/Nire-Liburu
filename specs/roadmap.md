# Дорожная карта реализации

Статус: Утверждена (проектирование); выполнение начинается только по явной команде владельца

Этот файл — план выполнения по созданию Android-приложения Nire-Liburu v1 на основе
спецификаций этого репозитория. Он не меняет ни одного решения: каждая задача ссылается
на ADR или доменную спеку, которая её регламентирует. Выполнение не начинается, пока
владелец явно не прикажет его начать.

> **Примечание о стеке.** Владелец заменил технологический стек: вместо
> Kotlin/Compose/Room (ADR-005) используется стек эталонного проекта TuneDraft —
> Expo + TypeScript (React Native), рендеринг `@shopify/react-native-skia`,
> хранение — JSON-файлы (expo-file-system) + AsyncStorage, жесты —
> react-native-gesture-handler + reanimated, сборка
> APK локально (`npx expo run:android` / `eas build --local`); механизм входа
> Google фиксируется точкой решения в T0.2. Упоминания старого
> стека в этом файле заменены; формальная фиксация нового стека отдельным ADR
> (по правилу WORKFLOW: принятый ADR не правится) — отдельная задача.

Источники истины (порядок чтения для любой задачи): [INDEX.md](./INDEX.md) →
[architecture/overview.md](./architecture/overview.md) → указанная доменная спека/ADR.

### T0.1 Создать каркас Expo/React Native-проекта

- Что: Пустой Expo-проект со стеком TuneDraft (см. примечание о стеке; формальная

- Как: Expo + TypeScript (React Native), рендеринг `@shopify/react-native-skia`;

- Где: корень репозитория (новый Expo-проект; это дерево specs/ остаётся
  первоисточником).
- Критерии приёмки:

    репозитория.

    в портретной ориентации.
  - В манифесте присутствует `allowBackup=false`; правила бэкапа запрещают любой
    перенос данных.
  - Набор зависимостей соответствует примечанию о стеке (без лишних
    фреймворков).

## Фаза 1 — Слой данных

### T1.1 Модель идентичности книги и прогресса

- Что: Типы и чистые функции для bookId и документов прогресса.
- Как: `bookId = sha256(content)[0..16)` — 16 символов hex в нижнем регистре
  (ADR-002); JSON-схема прогресса v1 — в точности как в
  [contracts/drive-storage.md](./contracts/drive-storage.md); сравнение LWW
  (updatedAt, затем revision, затем deviceId) как чистая функция с юнит-тестами;
  типы позиций: `charOffset` для txt/fb2, `page` для pdf — никакого третьего вида.
- Где: новые пакеты `core/model` и `core/identity`.
- Критерии приёмки:
  - Юнит-тесты: одинаковые байты → одинаковый bookId на разных запусках
    и устройствах; fb2 и fb2.zip одного содержимого дают одинаковый bookId после
    распаковки (правило распаковки при импорте, ADR-004).
  - Тесты LWW покрывают все ветки разрешения ничьих и входные данные
    с разными часовыми поясами/рассинхроном часов.
  - Сериализация JSON со стабильным порядком ключей обеспечивает побайтово
    точный round-trip документа прогресса (golden-file тест).

### T1.2 Схема локального хранилища и репозитории

- Что: Локальное хранение книг и ожидающих операций синхронизации.
- Как: Записи каталога `BookRecord` (id, displayName, author, format, addedAt,
  lastReadAt, needsDownload, driveFileId nullable, localUri nullable) — в
  JSON-файле каталога (expo-file-system, стиль TuneDraft: стабильное имя файла,
  атомарная запись); очередь синхронизации `PendingOp` — отдельное хранилище
  (AsyncStorage). Репозитории за интерфейсами; импорты Google/Drive в этом
  слое запрещены (правило анти-паттернов из overview). Выборки для: сетки
  библиотеки с сортировкой по lastReadAt по убыванию, где null-lastReadAt
  всегда в конце (ADR-011); книги, требующие скачивания; ожидающие операции
  по bookId.
- Где: пакет `data/local`; репозитории в `data/repo`.
- Критерии приёмки:
  - Юнит-тесты репозиториев: инвариант сортировки соблюдается (null-last
    всегда после читавшихся, стабильность внутри групп согласно решению T0.2).
  - Интерфейсы репозиториев компилируются без каких-либо зависимостей
    от Drive/сети.
  - Карточка «только метаданные» (`needsDownload=true`, `localUri=null`)
    корректно проходит запись/чтение; каталог переживает смерть процесса.

## Фаза 2 — Форматы: движок txt + fb2

### T2.1 Парсеры (определение кодировки txt, XML fb2)

- Что: Поток байтов → текст; fb2 → структурированное тело + метаданные.
- Как: txt: автоопределение кодировки BOM → UTF-8 → windows-1251 (ADR-004);
  fb2: XML pull-разбор body/section в плоский список глав (заголовок + диапазон
  charOffset, оглавление в v1 — ADR-008) плюс title/authors/cover для метаданных;
  fb2.zip: принимается ровно одна запись, распаковка при импорте, сообщения
  об ошибках для 0 или 2+ записей (ADR-004).
- Где: пакеты `formats/txt`, `formats/fb2`.
- Критерии приёмки:
  - Golden-file тесты: UTF-8 с BOM и без, UTF-16 с BOM, образец windows-1251;
    мусор в неверной кодировке даёт понятную ошибку, а не кракозябры.
  - Фикстура fb2 с 3 секциями даёт плоское оглавление с корректными
    смещениями символов.
  - Zip с 1 записью — ОК; 0 и 2+ записей дают задокументированные ошибки.

### T2.2 Движок пагинации (детерминированный reflow)

- Что: Тот же viewport → те же страницы; соответствие charOffset ↔ страница.
- Как: Разбиение текста на страницы при заданном viewport (размер шрифта в v1
  фиксирован, ADR-006); чистое, тестируемое ядро, отделённое от UI (React
  Native/Skia);
  кэш по bookId + подписи viewport; переход по слайдеру отображает целевую
  страницу → charOffset и обратно (ADR-010, п. 6); NavMode влияет только на
  представление: VERTICAL_SCROLL (по умолчанию) и HORIZONTAL_PAGING используют
  одни и те же страницы (ADR-008).
- Где: пакет `formats/pagination`.
- Критерии приёмки:
  - Property-тест: paginate(text, viewport) детерминирован — одинаковые входы
    дают одинаковые границы страниц (спека: одинаковые входы → одинаковая
    пагинация).
  - Round-trip тест: charOffset → страница → charOffset возвращает то же
    смещение.
  - Производительность: пагинация txt на 2 МБ при среднем viewport укладывается
    в локально задокументированный бюджет; движок не содержит импортов
    UI-компонентов (React Native/Skia).

### T2.3 Путь рендеринга PDF

- Что: Платформенный PdfRenderer (через тонкий нативный модуль Expo) за той же
  моделью позиций.
- Как: Битмапы страниц по ширине экрана; pinch-zoom + панорамирование — только
  визуально, не сохраняется, сбрасывается к «по ширине» при перелистывании
  (ADR-009, п. 3); прогресс = номер страницы; зоны нажатия те же, что
  у текстовых форматов; без оглавления PDF в v1 (ADR-010, п. 7); LRU-кэш
  битмапов ограничен бюджетом из T0.2.
- Где: пакет `formats/pdf`.
- Критерии приёмки:
  - Фикстурный PDF рендерит все страницы; прогресс сохраняется как страница
    и переживает смерть процесса.
  - Кэш никогда не превышает задокументированный бюджет в стресс-тесте.
  - Никакой специфичный для pdf тип позиции не утекает за пределы
    `formats/pdf`.

## Фаза 3 — Библиотека

### T3.1 Конвейер импорта (системный выбор файлов, множественный выбор)

- Что: Выбор файла → хэш → метаданные → хранилище каталога, один общий конвейер.
- Как: expo-document-picker (SAF `ACTION_OPEN_DOCUMENT` под капотом)
  с множественным выбором (ADR-010, п. 4);
  для каждого файла: сохранение через SAF, sha256 → bookId, извлечение
  метаданных (fb2) или имени файла (txt/pdf), сначала распаковка fb2.zip;
  дубликат (тот же bookId) → no-op с уведомлением по каждому файлу, позиция
  не трогается (ADR-006); без разрешений на хранилище — только SAF (ADR-006);
  без поддержки переименования (ADR-009, п. 5).
- Где: пакет `library/import` + флоу в доменных README.
- Критерии приёмки:
  - Импорт смешанного множественного выбора (txt + fb2 + fb2.zip + pdf)
    создаёт все карточки с корректными метаданными; сбой одного файла
    не прерывает остальные.
  - Повторный импорт существующей книги не трогает lastReadAt и прогресс
    и показывает уведомление о дубликате.
  - Приложение не запрашивает runtime-разрешения на хранилище.

### T3.2 UI сетки библиотеки

- Что: Адаптивная сетка обложек с сортировкой и точкой входа удаления.
- Как: Адаптивная сетка 2–3 колонки (ADR-008): обложка или стилизованный
  по формату плейсхолдер, название, автор, процент прочитанного; долгое
  нажатие → диалог удаления из ADR-008 («везде» / «только локально» /
  одно действие для локальных книг); нажатие всегда открывает книгу;
  без иконок и множественного выбора на карточках (ADR-011); pull-to-refresh
  и автообновление `listBooks()` в облачном режиме (исключение «на переднем
  плане» из ADR-003).
- Где: пакет `library/ui`.
- Критерии приёмки:
  - Сетка корректно обновляется при изменениях хранилища каталога; процент
    соответствует документам прогресса.
  - Долгое нажатие на облачной книге показывает диалог из двух вариантов;
    на локальной — единственное удаление; нажатие никогда не удаляет.
  - UI-тесты (React Native testing library): инвариант сортировки виден;
    карточка «только метаданные» рендерит плейсхолдер и состояние скачивания.

## Фаза 4 — Читалка

### T4.1 Экраны читалки для txt/fb2 и pdf

- Что: Одна оболочка читалки, два рендерера, одинаковая обвязка и жесты.
- Как: Зоны нажатия (левая треть — назад, правые две трети — вперёд) везде,
  включая масштабированный PDF (ADR-006/ADR-009, п. 3); NavMode из настроек,
  по умолчанию VERTICAL_SCROLL (ADR-008); иммерсивный полноэкранный режим,
  панели через жест; `FLAG_KEEP_SCREEN_ON` (ADR-006); без выделения текста,
  долгое нажатие инертно (ADR-009, п. 6); восстановление точной позиции при
  повторном открытии.
- Где: пакет `reader/ui`.
- Критерии приёмки:
  - Повторное открытие после смерти процесса восстанавливает ту же позицию
    во всех трёх форматах и обоих NavMode.
  - Скриншот-тесты: иммерсивное состояние, оба NavMode, плейсхолдеры обложек.
  - Долгое нажатие не даёт ни выделения, ни меню ни в одном формате.

### T4.2 Плавающее меню, оглавление, слайдер

- Что: Всегда видимая полупрозрачная кнопка меню; панель с позицией, слайдером,
  главами, настройками, закрытием.
- Как: По ADR-010 п. 1/п. 6 и ADR-008: панель показывает «процент · страница x
  из N» (pdf: страница x из N); слайдер отображается в charOffset/страницу,
  отпускание сохраняет позицию точно как перелистывание; плоский список глав
  fb2 прыгает по charOffset; закрытие возвращает в библиотеку с сохранённой
  позицией.
- Где: пакет `reader/ui/menu`.
- Критерии приёмки:
  - Отпускание слайдера сохраняет позицию, переживающую повторное открытие.
  - Нажатие на главу позиционирует на начальное смещение главы (fb2); пункты
    меню для оглавления pdf отключены, без мёртвого UI.
  - Кнопка меню не перехватывает события зон нажатия вне своих границ.

## Фаза 5 — Облако: авторизация + синхронизация Drive

### T5.1 Вход через Google, режимы, раздел аккаунта в настройках

- Что: Вход через Google (expo-auth-session); режимы LOCAL/CLOUD; выход из аккаунта.
- Как: ADR-001/ADR-010 п. 2: единственный Drive scope — только
  `drive.file` (ADR-007); экран приветствия при первом запуске с «Войти через
  Google» / «Пропустить — локальный режим» (ADR-008); экран настроек из тулбара
  библиотеки с разделом «Аккаунт» (email, режим, выход) и разделом «Читалка»
  (NavMode) — единственная точка выхода из аккаунта.
- Где: пакет `auth/`; экраны по доменному README.
- Критерии приёмки:
  - Экран согласия показывает ровно Drive file scope; нигде в коде
    не запрашивается appdata scope.
  - Выход возвращает на приветствие; повторный вход в тот же аккаунт
    не показывает диалог смены аккаунта (ADR-003).
  - Вход под другим аккаунтом предлагает выбор: слить-загрузить или
    использовать библиотеку этого аккаунта, причём во втором варианте локальные
    книги остаются локальными с очищенным `driveFileId` (ADR-003; флоу смены
    аккаунта в overview).

### T5.2 Адаптер хранилища Drive

- Что: Единственный модуль, которому разрешено вызывать Drive API.
- Как: Реализовать [contracts/drive-storage.md](./contracts/drive-storage.md)
  в точности: видимая папка `Nire-Liburu/` для книг, `Nire-Liburu/progress/`
  для JSON прогресса (ADR-007); `listBooks()` игнорирует папку прогресса;
  интерфейсы DriveBooks/DriveProgress, включая `delete(bookId)`; ошибки Drive →
  типы ошибок синхронизации по таблице соответствий контракта; лимит мобильного
  трафика: молча ≤ лимита, диалог подтверждения выше лимита на тарифицируемой
  сети, Wi-Fi никогда не спрашивает, отказ оставляет карточку «только
  метаданные» (ADR-010, п. 5).
- Где: пакет `sync/drive` (единственный пакет, импортирующий типы Drive).
- Критерии приёмки:
  - Набор контрактных тестов проходит против тестового двойника Drive И живого
    смоук-аккаунта: upload/list/download/delete для книг и прогресса.
  - Таблица соответствия ошибок полностью покрыта юнит-тестами.
  - `listBooks()` никогда не возвращает JSON-файлы прогресса; логика диалога
    тарифицируемой сети покрыта юнит-тестами на граничных значениях из T0.2.

### T5.3 Синхронизация открытия/закрытия, очередь повторных отправок, повышение режима

- Что: Скачивание при открытии, отправка при закрытии, надёжный retry,
  однократное слияние.
- Как: Флоу ADR-003, включая НОВОЕ УСТРОЙСТВО (сразу карточки с метаданными,
  скачивание при первом открытии с проверкой хэша), pull-to-refresh/обновление
  при входе в библиотеку, retry фоновой очереди с backoff из T0.2; ручное удаление
  файла в Drive → тихое удаление карточки до «только метаданные»
  (`BookFileMissing`); порядок полного удаления: запись каталога+файл → файл Drive →
  прогресс Drive, 404 = успех (ADR-008 + контракт); однократное слияние при
  переходе с локального режима на облачный (ADR-003).
- Где: пакет `sync/`; фоновая очередь синхронизации регистрируется на уровне
  приложения.
- Критерии приёмки:
  - Интеграционный тест с фейковым Drive: закрытие офлайн ставит в очередь,
    очередь повторяет, сходится без дубликатов; LWW выбирает более новый
    документ в обоих направлениях.
  - Флоу нового устройства: карточки появляются без скачивания файла; первое
    открытие скачивает один раз (без повторного скачивания при втором
    открытии).
  - Ручное внешнее удаление файла Drive и последующее обновление удаляет
    только карточку; локальный файл приложение никогда не удаляет.
  - Тест прерывания полного удаления: убийство приложения посреди порядка
    оставляет состояние, которое очередь завершает при следующем запуске
    (идемпотентный порядок по контракту).

## Фаза 6 — Настройки, приветствие, локализация

### T6.1 Финализация экранов настроек и приветствия

- Что: Полный экран настроек и приветствие при первом запуске согласно
  ADR-008/ADR-010.
- Как: Разделы настроек: «Аккаунт» + «Читалка» (радио NavMode); приветствие
  один раз за цикл выхода; пустое состояние и текст приветствия упоминают
  удаление долгим нажатием (известный недостаток из ADR-011); текст
  о находимости долгого нажатия живёт в strings.
- Где: пакеты `settings/`, `onboarding/`.
- Критерии приёмки:
  - Чистая установка показывает приветствие ровно один раз перед библиотекой;
    после выхода оно показывается снова.
  - Смена NavMode вступает в силу при следующем открытии читалки без
    перезапуска.
  - Каждая строка в i18n-словаре; никакого захардкоженного видимого
    пользователю текста.

### T6.2 Полнота RU/EN

- Что: По умолчанию русский, полный английский, третий язык откатывается
  на русский.
- Как: базовый язык — русский, английский — полная параллельная ветка словаря
  (ADR-010, п. 3);
  проверка полноты словаря в CI; аудит форматов/множественных форм
  (страницы, процент).
- Где: пакеты `i18n/` (словари RU/EN).
- Критерии приёмки:
  - Скрипт проверки полноты словаря (`npm run typecheck` + отдельная проверка
    ключей) не сообщает об отсутствующих переводах.
  - Устройство с третьим языком (напр. de) показывает русские строки,
    а не ключи.

## Фаза 7 — Укрепление беты

### T7.1 Проверка режимов отказа и аудит инвариантов

- Что: Пройти по каждому инварианту из спецификаций и добавить тест или
  задокументированную причину, по которой он не может нарушиться.
- Как: Источник чек-листа: секции инвариантов в
  [architecture/overview.md](./architecture/overview.md) и четырёх доменных
  README; включить: никогда не существует третьего вида позиции;
  синхронизация никогда не в фоне, кроме входа в библиотеку/обновления;
  нет разрешений на хранилище; нет бэкапа ничего; граница единственного
  Drive-пакета (архитектурные анти-паттерны).
- Где: тестовые исходники; находки добавляются в секцию changelog этого файла.
- Критерии приёмки:
  - Каждый инвариант имеет именованный тест или письменное обоснование
    в описании PR; ноль неотмеченных пунктов в таблице аудита.

### T7.2 Релиз бета-APK

- Что: Подписанная бета-сборка, распространяемая для тестирования.
- Как: По ADR-006: бета-APK, оба scope нечувствительны, поэтому строгая
  проверка не нужна; release-профиль Expo: minify + proguard-правила
  нативных библиотек; бета-схема версионирования.
- Где: конфиг CI + release-профиль.
- Критерии приёмки:
  - Release-сборка создаёт подписанный APK (`npx expo run:android
    --variant release` или `eas build -p android --local`), который
    устанавливается
    и проходит ручной смоук: импорт → чтение → закрытие (синхронизация) →
    переустановка → восстановление на новом устройстве → прогресс на месте.
  - Во release нет флага debuggable; нет cleartext-трафика.

## Правила выполнения

1. Одна задача на ветку; критерии приёмки — определение готовности.
2. Никогда не править принятый ADR под код; написать новый ADR и пометить
   старый как частично заменённый (правило WORKFLOW).
3. Пути из «Где» каждой задачи создаются с нуля — кода ещё нет; при расхождении
   кода и спеки первоисточник — спека (чинить код).
4. Точки решений из T0.2 должны быть закрыты до фазы, которая их использует;
   результаты фиксировать в новых ADR или задокументированных константах.
